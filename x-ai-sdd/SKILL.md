# x-ai-sdd 方法论（AI 团队 SDD）

本 skill 是 SDD 通用方法论。任何关于 SDD 的写作、推进、审查、归档动作都先读它。

项目专属字段（仓库名、SDD 根目录、团队子目录划分、命名规则）由项目自己的 `.claude/skills/` 覆盖层 skill 提供。当项目没有提供覆盖时，本 skill 的默认值生效。

本 skill 只负责规范契约。README、brainstorm、research、plan、guide、runbook、issue、solution、全仓库 docs 信息架构与迁移治理交给 `x-ai-docs-builder`；同一任务涉及契约和项目级文档时联用两个 skill。

## 0. 触发场景速判

满足以下任意一条，立即进入本 skill：

- 用户说"写 SDD / 立 SDD / 推进 SDD / 验收 SDD"。
- 用户要新增或修改：表、接口契约、事件、payload、页面/路由/交互流、算法输入输出、模型评估口径、幂等键、补偿规则、调度规则。
- 用户在项目的 SDD 目录（默认 `docs/sdd/`，以项目覆盖为准）下创建或修改文件。
- 用户开始一个新功能且尚无对应 Feature SDD。
- 已经有实现但 SDD 未跟进（"先改 SDD 再改代码"原则被破坏）。

不触发：纯 bug 修复、拼写、局部重构、加日志、无业务语义变化的改动。

## 1. 核心原则（不可妥协）

SDD 是：
- 项目事实来源。
- AI 编码的约束输入。
- 功能验收的依据。
- 后续团队接手时的业务边界说明。

SDD 不是：
- 事后流水账。
- 大而全需求说明书。
- 和代码长期不一致的废文档。
- 每个方法、类的注释集合。

铁律：
1. 先用 SDD 控边界。
2. 再按 SDD 写设计、代码、配置、模型处理和测试。
3. **实现偏离 SDD 时，先改 SDD，再改代码。**
4. SDD 不是越写越长，而是把草案逐步固化成开发契约。

## 2. 生命周期（统一四态）

```
draft → ready → implemented → accepted
```

| 状态 | 含义 | 转入条件 |
| --- | --- | --- |
| draft | 起草中，结构未稳 | 新建时默认 |
| ready | 边界、输入输出、验收标准齐全，可作为 AI 编码约束 | 开工前必须达到 |
| implemented | 代码已完成且与 SDD 对齐 | 实现完成后立即转 |
| accepted | 已通过验收 | 验收后转；仅当项目覆盖层启用归档目录时移动 |

推进规则：
- **开工前**：SDD 必须从 draft → ready。状态非 ready 的 SDD 不允许据此编码。
- **实现后**：状态 → implemented。
- **验收后**：状态 → accepted。
- **实现与 SDD 不一致**：必须先回 SDD 修改，再继续代码（哪怕只是一个字段）。

## 3. 统一章节结构（默认 17 节）

每份 SDD 默认使用以下章节。不同领域可以改名但不能缺少能力。

```
0.  文档状态
1.  本 SDD 负责什么
2.  本 SDD 不负责什么
3.  当前阶段目标
4.  输入来源
5.  输出结果
6.  核心流程
7.  核心规则
8.  涉及对象
9.  数据或字段要求
10. 幂等规则
11. 状态或生命周期规则
12. 审计或事件规则
13. 异常和人工处理
14. 与其他 SDD 的调用关系
15. 验收标准
16. 决策记录
17. 待确认问题
```

领域改名示例：

| 通用章节 | 算法 SDD | 前端 SDD |
| --- | --- | --- |
| 7. 核心规则 | 特征与模型规则 | 交互规则 |
| 8. 涉及对象 | 输入数据集 | 涉及页面和组件 |
| 9. 数据或字段要求 | 输出结果格式 | 入参、状态和展示字段 |
| 10. 幂等规则 | 重复执行规则 | （可去掉） |
| 11. 状态或生命周期规则 | 模型版本生命周期 | 页面状态生命周期 |
| 13. 异常和人工处理 | （保留） | 空状态、异常状态和权限处理 |
| 14. 与其他 SDD 的调用关系 | 与业务系统的调用关系 | 与后端接口的调用关系 |

### 3.1 图示约定（统一用 mermaid）

SDD 里的所有图示**一律用 mermaid 绘制，禁止 ASCII 框线图**。理由：mermaid 可在 GitHub / 多数 Markdown 渲染器里直接渲染、改起来不破版、diff 友好；ASCII 框线图对齐脆弱、几乎不可维护。

按图的类型选 mermaid 图种：

| 图的用途 | mermaid 图种 | 常见落点章节 |
| --- | --- | --- |
| 时序 / 交互流（请求-响应、事件转换、跨服务调用） | `sequenceDiagram` | §6 核心流程 |
| 状态机 / 生命周期 | `stateDiagram-v2` | §11 状态或生命周期规则 |
| 流程分支 / 依赖关系 / 架构 | `flowchart` | §6、§14 |
| 实体关系 / 数据模型 | `erDiagram` | §8 / §9 |

写完后核对：mermaid 代码块用 ```` ```mermaid ```` 围栏开、单独一行 ```` ``` ```` 闭，全文围栏成对（数量为偶数）。

#### 3.1.1 数据库可视化强制规则

出现以下任一情况时，数据库图示不是可选项：

- 新增或修改两张及以上存在关联的表；
- 表位于不同 database/schema，通过业务键形成逻辑关联；
- 引入 checkpoint、租约、Outbox、delivery、失败状态或其他需要解释一致性边界的状态表；
- 一张源表的变化会驱动三张及以上下游表或外部存储。

此时必须同时满足：

1. 在 §8 / §9 使用 Mermaid `erDiagram` 表达表、主键和主要关联。
2. 跨 database/schema 的连线必须在图后注明“逻辑关联，非物理外键”；真实外键与业务关联
   不得混写成同一种数据库约束。
3. 数据跨服务、数据库或外部存储流动时，在 §6 增加 `flowchart` 或 `sequenceDiagram`，
   标明事实源、写入方和状态落点。
4. 对象存在三个及以上状态，或涉及重试、补偿、租约接管时，在 §11 增加
   `stateDiagram-v2`。
5. 每张新增或修改的表仍须提供数据字典，至少包含字段、数据库类型、可空性、默认值、
   主键/唯一约束、外键或逻辑关联、索引、字段用途和数据来源。索引可单独列表，但不能省略。

只有一张独立表且不存在关联、状态流转或跨存储数据流时，可以不画 ER 图。图示用于辅助理解，
不能替代字段表、约束、索引、规范性 DDL 或迁移说明。

## 4. 推荐目录结构（项目可覆盖）

默认结构：每个需求是 `feats/` 下的一个文件夹，SDD 主体写在该文件夹的 `README.md`，需求自带的图、数据样本、补充文档一起放在同一文件夹。

```
<项目 SDD 根>/                 # 默认 docs/sdd/
  README.md                    # 总入口、索引、状态汇总
  00-全局边界.md                # 跨需求公共规则（可选）
  01-工程规范.md                # 工程规范（可选）
  02-接口与事件规范.md          # 公共接口/事件规范（可选）

  feats/
    00-<需求名>/               # 数字前缀方便排序与稳定引用
      README.md                # 该需求的 SDD 主体
      ...                      # 该需求附属资产（图、数据样例、子文档）
    01-<需求名>/
      README.md
    02-<需求名>/
      README.md
```

约束（项目覆盖不能违反这些）：
- 每个需求是一个独立子文件夹，SDD 主体始终是该文件夹的 `README.md`。
- 需求子文件夹名应稳定（一旦被外部引用就不要重命名）。推荐使用数字前缀（如 `00-`、`01-`）保证排序与稳定引用。
- 状态（draft / ready / implemented / accepted）由 SDD 自身 §0 字段表达，不依靠"移动目录"。归档可选：项目覆盖层可决定是否引入 `feats/archived/` 子目录，但默认不强制。
- 公共规则（跨需求边界、工程规范、接口/事件协议）放 SDD 根目录的顶层文件，不混进 `feats/`。

具体路径、命名前缀规则、是否引入归档目录，以项目覆盖 skill 为准。

## 5. 拆分规则

**不要按代码结构拆 SDD。**

不推荐：一个 Controller / Service / Mapper / 页面组件 / 模型函数 / 表 / 方法 一个 SDD。

推荐拆分单位：
- 一个服务边界
- 一个业务能力
- 一个数据层
- 一个核心数据链路
- 一个事件协议
- 一个页面业务流
- 一个算法能力
- 一个长期维护的功能

何时必须拆：
- 单文件 > 20 页 → 考虑拆
- 单文件 > 30 页 → 基本必拆
- 小需求每次都要通读整篇 → 拆
- 多人经常同时改同一份 SDD → 拆
- AI 每次读入过多无关内容 → 拆

## 6. Feature SDD 模板

新增功能时，在 `feats/` 下创建一个新文件夹（默认命名 `<两位数字前缀>-<功能名>`，例如 `03-订单列表筛选`，项目可覆盖前缀规则），并把模板 `templates/feature-sdd.md` 复制为该文件夹的 `README.md`。

需求附带的图、数据样例、补充说明都放进同一文件夹。

## 7. Feature SDD 与主 SDD 的关系

- 主 SDD（SDD 根目录下的 `README.md` 与 `00-/01-/02-` 顶层文件）保留：边界、公共规则、分层规则、通用接口/事件规则。
- Feature SDD（`feats/<feat>/README.md`）保留：具体功能的目标、流程、页面、接口、数据、模型、验收标准。
- 完成后：Feature SDD §0 状态 → accepted。是否额外移到归档目录由项目覆盖层决定。
- **不要**把 Feature SDD 全量合并进主 SDD。
- 只有沉淀出公共规则时，才反补主 SDD（顶层文件 / 根 README）。

## 8. AI 编码前的强制流程

按顺序读：

1. `AGENTS.md`（或 `CLAUDE.md`）
2. 项目 SDD 根目录的 `README.md`
3. 当前数据域或服务的 `README.md`
4. 当前任务对应的 SDD

如果对应 SDD 状态 != ready：**停下来，先把 SDD 推到 ready，再写代码。**

## 9. AI 禁止行为（硬约束）

- 跳过 SDD 直接写代码。
- 新增表 / 接口 / 事件 / 页面 / 模型契约 但不更新 SDD。
- 写出与 SDD 冲突的实现。
- 把 Feature SDD 全量合并进主 SDD。
- 用技术实现掩盖业务边界不清。
- 在 SDD 未明确时自行扩大实现范围。

## 10. AI 实现完成后必做

1. 对照 SDD §15 验收清单逐项自查。
2. 列出"已完成 / 未完成 / 无法验证"三类。
3. 实现过程中改了设计 → 反补 SDD。
4. SDD 状态 ready → implemented。

## 11. 必须先改 SDD 的代码变更

- 新增表 / 修改核心表语义
- 新增接口 / 修改接口契约
- 新增事件 / 修改事件 payload
- 新增页面 / 路由 / 关键交互流程
- 修改前端页面状态、权限或异常展示规则
- 新增算法模型 / 特征 / 输入输出 / 评估指标
- 修改算法回调格式或模型版本策略
- 改变幂等键 / 失败补偿方式
- 改变跨服务调用方向
- 改变任务调度 / 异步处理 / 重试规则

可以不改 SDD：修拼写、不改语义的局部 bug、重命名局部变量、补日志、不改契约的局部重构。

## 12. 接口、事件、异步协作规则

跨团队协作时，**先在 SDD 里说明，再编码**。

接口需说明：调用方、提供方、入参、出参、错误码、权限。
事件需说明：含义、触发时机、payload、幂等键、消费方。
异步任务需说明：触发方式、重试规则、失败处理、人工补偿方式。
算法调用需说明：输入数据、模型版本、输出格式、结果解释方式。
前端交互需说明：页面状态、加载状态、空状态、异常状态、权限状态。

### 事件命名

事件名表达"已经发生的事实"，不是"命令别人做什么"。

- 推荐：`order.payment.completed`、`model.inference.completed`
- 不推荐：`createOrderTask`

### 事件 payload 推荐结构

```json
{
  "event_id": "uuid",
  "event_type": "order.payment.completed",
  "event_version": "1.0",
  "tenant_id": "tenant-id",
  "aggregate_type": "order",
  "aggregate_id": "order-id",
  "occurred_at": "2026-05-18T10:00:00+08:00",
  "trace_id": "trace-id",
  "payload": {}
}
```

## 13. 验收标准写法（§15 节硬规则）

**必须可验证。** 含糊不能写。

不推荐：
- [ ] 数据正常同步。

推荐：
- [ ] 同一请求重复提交时，不产生重复业务记录。
- [ ] 接口返回空数据时，前端展示约定的空状态，不展示异常状态。
- [ ] 模型推理失败时，记录失败原因，并允许按 trace_id 排查。
- [ ] 同一 event_id 重复消费时，不产生重复副作用。
- [ ] 页面刷新后，筛选条件和分页行为符合 SDD 约定。
- [ ] 算法结果回调缺少必填字段时，服务返回明确错误并记录 trace_id。

更多对照见 `references/acceptance-examples.md`。

## 14. 维护节奏

**单人阶段：**
- 每天先补当天最小 SDD，不追求一次写全。
- 开工前推到 ready，实现后转 implemented，验收后转 accepted。

**多人阶段：**
- PR 必须检查是否需要更新 SDD。
- 改数据对象 / 接口 / 事件 / 页面流程 / 模型契约 → PR 必须带 SDD 变更。
- 重要功能必须有 Feature SDD。
- 过期 SDD 标记状态和替代方案，不直接删除。

**长期阶段：**
- 每周清理一次 draft。
- 每个版本发布前核对核心 SDD 与实现一致性。
- 公共规则沉淀到主 SDD；具体功能留在原 `feats/<feat>/` 文件夹（项目若启用归档目录，则迁入归档）。

## 15. 本 skill 的执行模式

收到 SDD 相关任务时，按下列分支处理：

### 分支 A：新建 Feature SDD
1. 在项目 SDD 根目录的 `feats/` 下创建新文件夹（命名规则以项目覆盖层为准，默认 `<两位数字前缀>-<功能名>`）。
2. 复制 `templates/feature-sdd.md` 为该文件夹的 `README.md`。
3. 填充 §0 文档状态（draft），§1 / §2（负责 / 不负责），§3（当前阶段目标）。
4. 推进到 ready 之前，§4-§5（输入/输出）、§15（验收标准）必须可读、可验证。
5. 在 SDD 根目录的 `README.md` 索引中加一行指向新文件夹。

### 分支 B：推进 SDD 状态
1. 读取目标 SDD 的 §0 文档状态。
2. 按 §2 生命周期校验当前状态是否满足下一态的转入条件（详见 `references/lifecycle-checklist.md`）。
3. 不满足 → 列出缺口，先补齐再推进。
4. 满足 → 修改 §0 状态字段并更新"最后更新"。
5. 状态转为 accepted 时，更新根 README 的状态汇总；若项目覆盖层启用了归档目录，再迁入归档目录。

### 分支 C：审查 SDD
按以下清单逐项核对，缺一项就指出来：
- [ ] §0 状态字段齐全且合法
- [ ] §1 / §2 边界清晰，没有"什么都管"
- [ ] §4 / §5 输入输出可读
- [ ] §9 字段或数据要求与代码现状一致
- [ ] §10 幂等规则明确（异步链路必须有）
- [ ] §14 调用关系闭环，引用的其他 SDD 存在
- [ ] §15 验收标准可验证（参考 §13）
- [ ] §17 待确认问题不为空（draft 阶段允许有，ready 阶段必须收敛）
- [ ] 命中 §3.1.1 条件时，§8 / §9 有 ER 图和完整数据字典
- [ ] 跨库关联已区分物理外键与逻辑关联
- [ ] 复杂数据流和状态流转分别在 §6 / §11 有对应 Mermaid 图

### 分支 D：代码变更触发 SDD 更新
1. 识别变更类型（参考 §11）。
2. 找到对应 SDD，若不存在 → 创建。
3. 先改 SDD 对应章节，再改代码。
4. 提交时把 SDD 与代码放在同一 PR。

## 16. 项目覆盖层契约

项目在 `.claude/skills/` 下可放一个 skill（同名 `x-ai-sdd` 或加项目后缀），用于固定本方法论留出的可变项：

- **SDD 根目录**（默认 `docs/sdd/`）
- **`feats/` 子文件夹命名规则**（默认 `<两位数字前缀>-<功能名>`）
- **是否启用归档目录**（默认不启用；项目可启用 `feats/archived/` 或类似约定）
- **是否需要按团队/域再分层**（默认不分层，所有需求扁平放在 `feats/` 下）
- **特殊领域章节改名**
- **项目级硬约束**（例如本仓 trace 字段名、租户字段名）

覆盖层 skill 不应重写本 SKILL.md 的方法论部分，只指明项目专属字段。AI 在执行 SDD 任务时：先读本方法论 → 再读项目覆盖层 → 取覆盖值生效。

## 17. 与 compound-engineering（`ce-*`）skill 的衔接

SDD 是事实来源与约束，`ce-*` 是把这套约束转成可执行动作的引擎。两者关系：**SDD 决定"做什么、做到什么算完"，`ce-*` 决定"怎么推进每一步"。**

把 SDD 生命周期映射到 `ce-*` 工具链：

| 节点 | 输入 | 推荐 ce skill | 与 SDD 的耦合点 |
| --- | --- | --- | --- |
| 立项前模糊期 | 一个想法、一段对话 | `ce-brainstorm` / `ce-ideate` | 产出物用来填充 SDD 草稿的 §1 / §2 / §3 |
| draft → ready 前自审 | 已起草的 SDD | `ce-doc-review` | 用 persona agents 审 §1 边界、§15 验收、§17 待确认项；满足 ready 校验单后再推进 |
| **ready 已锁** | 状态为 ready 的 SDD | **`ce-plan`** | SDD 作为强约束输入，产出实现计划；计划不得引入 SDD 未声明的契约 |
| **照计划落地** | ready SDD + 实现计划 | **`ce-work`** | 实现期把 §15 验收清单当完工判据，§9 / §11 当字段与状态约束；偏离立即回 SDD |
| 提交前 | 已实现的代码 + ready SDD | `ce-code-review` | 把 SDD 当合同审；任何"代码新增/修改"但未在 §8/§9/§12 出现的项一律标红 |
| 实现验证 | 已实现的代码 | `verify` / `ce-test-browser` | 逐条跑 §15；产出"已完成 / 未完成 / 无法验证"三类清单 |
| 起 PR | 验收通过的代码 + SDD | `ce-commit-push-pr` | SDD 与代码必须同 PR；PR 描述引用 SDD 路径 |
| 验收沉淀 | accepted 的 SDD + 复盘 | `ce-compound` | 把跨需求的公共规则反补主 SDD；具体功能留在原 `feats/<feat>/` 文件夹 |
| 偶发 bug 修复 | 现有 SDD + 失败现象 | `ce-debug` | 仅当根因暴露契约缺陷时回改 SDD；纯实现 bug 不动 SDD |

### 硬规则

1. **`ce-plan` 不允许在 SDD 状态非 ready 时启动。** 状态为 draft 的 SDD 先用 `ce-doc-review` / 手动补齐到 ready，再进入 `ce-plan`。
2. **`ce-work` 期间发现需要新增表 / 接口 / 事件 / 字段 / 状态，必须先回 SDD 改 §8/§9/§11/§12，再继续写代码**（铁律 §1.3）。中断 `ce-work` 没关系，比写出和 SDD 冲突的代码代价小。
3. **`ce-code-review` 与 SDD 冲突的判定优先级高于风格 / 性能 / 简化**。若 SDD §15 没要求某项检查，不要让 reviewer 临时发明硬性要求；要么补进 SDD，要么不在本 PR 卡。
4. **`ce-compound` 输出不能替代 SDD**。`docs/solutions/` 下的 learnings 是 know-how，不是契约；契约只能在 SDD。
5. **`ce-brainstorm` / `ce-ideate` 不产 SDD，只产草料**。在它们之后必须显式进入本 skill 的"分支 A：新建 Feature SDD"。

### 触发关系

用户说"开始实现 feats/03-xxx" / "ce-plan 这个需求" / "ce-work 这块" 时：

1. 先用本 skill **分支 B** 检查目标 SDD 状态。
2. 状态非 ready → 阻止 ce-plan / ce-work，转分支 B 推进到 ready。
3. 状态为 ready → 把 SDD 路径、§15 验收清单、§9/§11 约束作为上下文交给 `ce-plan` / `ce-work`。
