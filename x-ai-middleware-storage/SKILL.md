# x-ai-middleware-storage — 中间件存储治理

诊断 Docker/Compose 中间件的容量、增长和保留策略；在明确确认后安全清理，并验证服务与业务数据。

## 红线

- 默认只读。禁止直接 `rm` 数据库数据目录、Docker 卷或用途不明的文件。
- 不把“检查”“解释风险”当成清理授权；不可逆操作必须单独取得明确确认。
- 清理前必须展示精确目标、当前大小、数据用途、预计释放量、不可逆影响和恢复可能性。
- 变更配置的授权不自动包含重启；热加载失败时停止并请求新的重启授权。
- 凭据只从已有 SSH 配置、容器环境或环境变量读取，不打印、不写入命令参数、脚本或 Skill。
- 远程操作复用 `x-ai-ssh-remote` 的连接决策与凭据规则。

## 决策流程

1. **确认意图**：区分只读盘点、原因诊断、治理方案和执行清理。
2. **识别部署**：确认宿主机、Compose 项目、容器、卷、网络和配置来源；标签里的旧路径必须验证存在性。
3. **建立基线**：记录文件系统总量/已用/可用、容器健康和启动时间。
4. **拆分占用**：优先使用数据库系统表、管理指标或对象存储 API；对数百万小文件避免无界 `du`。
5. **估算增长**：使用完整自然日和最近 7 天；今天只能作为部分日展示，不能混入日均值。
6. **分类数据**：区分业务数据、数据库系统日志、容器日志、缓存、临时文件和历史备份。
7. **提出措施**：按日志降级、TTL/保留期、安全清理、扩盘/迁移的顺序给出方案。
8. **确认门禁**：执行任何不可逆动作前停下，向用户展示清单并取得明确确认。
9. **执行与验证**：最小化变更范围；核对磁盘、容器健康、启动时间、业务表及代表性查询。

## 容量与增长率

优先级从高到低：

1. 中间件自身按日存储指标或分区字节数。
2. 对象存储的桶字节数、对象数和按日新增对象数。
3. 数据库表总压缩字节数 ÷ 总行数 × 每日新增行数。
4. 两次相隔足够时间的文件系统快照。

报告至少包含：

- 当前总容量、可用空间和使用率。
- 各中间件已知占用及未解释差额。
- 昨日增量、近 7 个完整自然日日均和峰值。
- 计算公式、压缩/对象平均大小等假设及误差来源。
- 按日均与峰值计算的预计剩余天数。

不要把累计表大小除以运行天数作为唯一结论；保留策略、历史迁移和流量趋势会让它失真。

## 清理确认模板

执行前向用户明确列出：

```text
目标：<database.table / log files / bucket prefix>
当前占用：<size>
用途：<业务数据 / 诊断日志 / 缓存>
动作：<TRUNCATE / TTL / 删除过期分区 / 日志降级>
预计释放：<size or range>
不可逆影响：<会丢失什么>
运行影响：<无停机 / 后台合并 / 可能短暂阻塞>
回滚：<可回滚方式，或明确不可恢复>
```

只有用户对该精确目标明确同意后才执行。若目标、表名、环境或范围变化，重新确认。

## 配置变更规则

- 使用独立覆盖文件，不直接改镜像内主配置。
- 写入临时文件，先做语法/配置解析校验，再原子替换。
- 优先热加载并记录变更时间；制造代表性请求后按时间窗口验证。
- 验证窗口排除旧缓冲日志。热加载未生效时停止，不自动重启。
- 容器内文件只在当前容器生命周期内持久；需要在 Compose 中以宿主机文件或配置卷挂载。
- Compose 服务定义缺失或标签路径失效时，禁止盲目 `docker compose up --force-recreate`。

## 验证清单

- `df` 的已用/可用空间符合预期，且没有异常继续下降。
- 目标容器仍为 running/healthy，启动时间证明是否发生过重启。
- 业务表仍存在，行数/大小合理，代表性读查询成功。
- 新日志级别、TTL 或保留策略已从有效配置/表定义确认。
- 清理后的日志会重新产生时，说明新的增长速度和下次风险时间。
- 告知用户变更的持久化范围，以及是否还欠 Compose 挂载或重启窗口。

## 场景路由

- Langfuse、ClickHouse `system.*_log`、MinIO 桶、PostgreSQL、Redis：必须阅读 [references/langfuse-clickhouse-minio.md](references/langfuse-clickhouse-minio.md)。
- 尚无配方的中间件：沿用通用流程，只做可验证的发现；不要套用 Langfuse 的容器名、表名或安全结论。
