# 文档路由决策

## 四个判断维度

对内容依次提问：

1. **谁读取**：首次使用者、开发者、评审者、运维者还是未来决策者？
2. **是否已决定**：仍在探索、已有证据、已形成契约，还是已经验证完成？
3. **是否权威**：它描述必须遵守的事实，还是说明、计划、经验或未闭环事项？
4. **读完做什么**：理解、决策、实现、操作、处理问题还是复用解决方案？

## 决策树

```text
是否是首次了解或第一次成功操作？
├─ 是 → 根 README
└─ 否
   是否是执行任务必须遵守的仓库规则？
   ├─ 是 → AGENTS.md
   └─ 否
      是否仍在发散候选方案？
      ├─ 是 → brainstorms
      └─ 否
         是否以实验、对比或外部资料为主要证据？
         ├─ 是 → research
         └─ 否
            是否定义可验证的系统行为或契约？
            ├─ 是 → sdd，并联用 x-ai-sdd
            └─ 否
               是否说明选定方案或实施顺序？
               ├─ 是 → plans
               └─ 否
                  是否是重复执行的稳定操作？
                  ├─ 开发/使用 → guides
                  ├─ 部署/运维/恢复 → runbooks
                  └─ 否
                     是否仍需处理或决策？
                     ├─ 是 → issues
                     └─ 已验证根因与方案 → solutions
```

## 容易混淆的边界

### README 与 guide

README 让读者完成第一次成功操作；guide 覆盖完整、重复和分角色使用。README 中超过一屏的配置矩阵、API 示例或排障步骤通常应下沉。

### research 与 brainstorm

brainstorm 允许假设和候选；research 必须写来源、方法、观测和结论边界。一次 POC 如果产出了证据，归 research。

### SDD 与 plan

SDD 定义“必须满足什么”；plan 定义“准备怎样实现”。实现顺序变化不应迫使契约重写，行为变化则必须更新 SDD。

### guide 与 runbook

guide 面向正常调用、配置和开发，配置误用的简短 FAQ 也可保留；runbook 面向具体环境、权限、生产诊断、风险操作、部署、故障恢复、验证和回滚。已验证根因与长期修复经验进入 solution。

### issue 与 solution

issue 保存未闭环状态和下一步；solution 只记录已经验证的根因、修复和适用条件。issue 关闭时可链接 solution，不把原文件搬过去。

### API 文档

- 先区分 Python SDK 返回模型、HTTP response envelope、事件协议和流式帧，不能因都叫“响应”就强行统一。
- 请求/响应、错误语义、兼容性：对应模块的 SDD。
- 调用示例、鉴权准备、常见用法：guide。
- OpenAPI 自动生成参考：仓库既有 reference 或生成站点。
- 接口响应规范尚未统一：issue，必要时链接 research 和未来 SDD。

## 常见请求示例

| 请求 | 路由 |
| --- | --- |
| “README 太长，把细节挪出去” | README 保留入口；细节按 guide/runbook/SDD 分类 |
| “记录我们还没有统一的响应格式” | `issues/`，`type: decision` 或 `todo` |
| “比较三个向量数据库” | `research/`；选型仍未收敛时链接 brainstorm |
| “定义批量导入接口” | `sdd/` + `x-ai-sdd`；实施拆到 plan |
| “写测试环境部署方法” | `runbooks/` |
| “记录这次线上事故怎么修好的” | `solutions/`；操作恢复步骤可另进 runbook |
| “列出下季度要补的文档” | `issues/` 的 TODO 索引，不新建平行 todo 体系 |

## 多类型内容

一篇文档同时承担多个角色时优先拆分：

- 把外部调研证据留在 research。
- 把最终行为约束写入 SDD。
- 把执行步骤写入 plan。
- 把稳定操作沉淀为 guide 或 runbook。

短小且不会产生独立生命周期的附属信息可以留在主文档，但要明确章节角色。
