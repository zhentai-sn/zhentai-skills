# 中间件存储治理技能设计

## 目标与边界

新增 `x-ai-middleware-storage`，面向 Docker / Docker Compose 中间件，处理磁盘容量、每日增长率、日志与数据保留策略、安全清理。首版以 Langfuse 的 ClickHouse、MinIO、PostgreSQL、Redis 组合为完整案例，同时保留扩展 MySQL、Kafka、Elasticsearch 等场景的结构。

该技能不负责通用部署、业务数据查询、性能调优、备份恢复或版本升级；分别交给已有部署、数据库和排障技能。

## 内容结构

- `SKILL.md`：保存通用治理流程、决策规则、安全门禁和资源路由。
- `references/langfuse-clickhouse-minio.md`：保存 Langfuse 场景配方，包括容量拆分、增长估算、ClickHouse 系统日志治理、MinIO 指标读取和热更新验证。
- `agents/openai.yaml`：提供 Codex 技能列表的展示名称、短描述和默认提示词。

首版不提供自动清理脚本。当前只有一个经过验证的真实案例，脚本化容易把特定容器名、网络名和目录结构误当成通用约定；保留命令模板和发现步骤更安全。

## 通用工作流

1. 识别宿主机、Docker/Compose 项目、容器、卷和磁盘风险。
2. 拆分各中间件占用，优先使用数据库系统表、管理指标或对象存储 API，避免对海量文件直接运行长时间 `du`。
3. 用完整自然日和最近 7 天计算增长率，区分当日未完成数据；说明估算公式、压缩率和对象平均大小等假设。
4. 区分业务数据、系统诊断日志、容器日志、缓存和可回收历史数据。
5. 按低风险到高风险提出日志降级、TTL、分区清理、扩盘或迁移方案。
6. 对不可逆操作展示精确目标、当前大小、用途、可释放空间、影响和恢复可能性，取得用户明确确认。
7. 执行后核对磁盘、容器健康、启动时间、业务表存在性及代表性查询。

## Langfuse 首版配方

- 识别 Langfuse Web/Worker、ClickHouse、MinIO、PostgreSQL、Redis 容器和卷。
- 用 ClickHouse `system.tables`、`system.parts` 和按日业务记录估算业务数据与系统日志增长。
- 用 MinIO Prometheus 管理指标读取桶总字节数与对象数；在全量 `du` 超时时避免继续施压。
- 说明 `system.text_log` 是 ClickHouse 诊断日志而非 Langfuse 业务数据；优先用 SQL `TRUNCATE`，禁止删除 ClickHouse 底层文件。
- 将 `logger.level` 与 `text_log.level` 从 `trace` 降至 `information`，设置 7 天 TTL，并区分配置热加载与容器重建后的持久化问题。
- 处理 Compose 标签路径失效、当前 Compose 已移除中间件服务、运行容器为旧部署遗留等情况；未恢复服务定义前禁止盲目重建。
- 提醒 PowerShell、SSH、Bash 多层引号和 CRLF 问题，优先使用远端脚本标准输入、Base64 内容传输和原子替换。

## 安全与失败处理

- 默认只读；禁止直接 `rm` 数据库数据目录、Docker 卷或用途不明的文件。
- 清理必须按“诊断 → 影响说明 → 明确确认 → 执行 → 验证”推进。
- 配置变更使用独立覆盖文件、语法校验、原子替换和失败回滚。
- 热加载后按时间窗口制造代表性请求并验证新日志级别；未生效则停止，不自动重启。
- 需要重启时单独申请时间窗口和授权，不把热更新授权扩大为重启授权。
- 凭据只从已有 SSH 配置、容器环境或环境变量读取，不输出、不写入技能文件。

## 验证标准

- 技能目录通过 `quick_validate.py`。
- `agents/openai.yaml` 与触发范围一致。
- README 技能清单和安装命令包含新技能。
- 场景配方明确区分只读命令、需确认的破坏性命令和重启操作。
- 本机安装副本与仓库源目录一致。
- 仓库改动提交并推送，且提交信息不包含模型署名。
