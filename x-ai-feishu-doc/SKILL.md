# 飞书长文档协作整理

用户在飞书上写长文档（调研、技术方案、汇报），让你逐节整理。这个技能管**判断**：内容该用什么形式承载、主线怎么串、改稿时哪些能碰哪些不能碰。机械操作走 [`lark-doc`](../lark-doc/SKILL.md)。

## 先分清三个技能

| 技能 | 管什么 |
| --- | --- |
| `lark-doc` | 飞书 CLI 怎么调：fetch / update / 画板 / block 定位 |
| **`x-ai-feishu-doc`（本技能）** | 在飞书上**和用户一起**整理长文档的风格、主线与排版 |
| `x-ai-docs-builder` | 仓库内 `docs/` 的信息架构与治理 |

长文档的初稿建议先在仓库 `docs/` 里落 Markdown，用户自己贴进飞书；**逐块改飞书慢且易与用户并发编辑冲突**。已经在飞书上的文档才用本技能逐节整理。

## 1 · 协作风格

### 铁律

| 规则 | 原因 |
| --- | --- |
| **不删用户已有内容**，要删先列出具体块和后果，等确认 | 用户的段落、表格、配色都是他自己排的 |
| **格式是用户的**：列宽、单元格底色、字重不要动 | 他会手动调；整表重写会静默抹掉 |
| **一条命令一次验证**，不要串起来只看最后一条的返回 | 曾经串命令导致前一条静默没生效，用户截图问「没有看到呢？」 |
| **改结构性内容前先 fetch 最新版** | 用户在并发编辑；凭记忆重建必冲掉他的改动 |
| 未经要求**不推送任何仓库** | 见各仓的自推约定 |

### 改稿的安全顺序

1. `docs +fetch --scope section --detail with-ids` 拿到**当前**块结构，不用缓存
2. 想清楚每一步动哪几个 block id，逐条执行、逐条看返回
3. 结构改完**重新 fetch**——替换标题块会换 block id，旧 id 立刻失效
4. 改完通读渲染结果，特别检查**交叉引用**是否还成立

### 撤回自己的改动

用户说「撤回刚刚的修改，我自己手动改」时，**不要凭记忆重建**——那样会丢掉他手调的列宽和配色：

```bash
lark-cli docs +history-list --doc <URL> --as user          # 找改动前的 revision
lark-cli docs +fetch --doc <URL> --scope section \
  --start-block-id <锚点> --detail full --revision-id <N>   # 取原貌（含样式）
# 去掉 id="..." 后 block_replace 写回
```

### 用户会逐句质疑

写进文档的每个数字和因果**先查证再落笔**：查库、读代码、查文献。查不动就标来源与局限（例：「厂商自建基准，需谨慎外推」）。被质疑时先核事实，错了直接改，不要辩护。

## 2 · 写作思路：一条贯穿全文的弧线

整篇文档要能被一句话串起来。默认弧线：

```text
背景 → 任务定性 → 相关工作 → 难点 → 实测/探索 → 方案 → 结果与验收
```

| 环节 | 这一节要回答 | 写砸的样子 |
| --- | --- | --- |
| **背景** | 为什么现在要做这件事 | 罗列现状，不说触发点 |
| **任务定性** | 这到底是个什么问题 | 直接跳进技术选型 |
| **相关工作** | 别人怎么解的，哪些思想仍然适用 | 堆项目清单，不提炼原则 |
| **难点** | 难在哪几个**互相独立**的维度 | 把同一个难点换词说三遍 |
| **实测 / 探索** | 我们自己测出了什么 | 只有结论没有数据 |
| **方案** | 因此我们决定做什么、按什么顺序 | 写成注意事项而不是步骤 |
| **结果与验收** | 怎么算做成了 | 没有可判定的通过线 |

### 两条硬要求

- **难点与方案必须一一对应**。难点列了 N 条，方案就要能逐条回答。**缺口宁可明写「缺」，也不要假装覆盖**——写出来的空白会自然逼出新的行动项。
- **结论先行**。每节开头一句能独立成立的判断，证据放后面。

## 3 · 结构选择

### 一个问题一张表

三个场景就是三行，不是三个三级标题。先问：这几段是不是在回答同一个问题？是就合成一张表。

### 同级才能放进同一张表

一张表只能有**一个可比维度**。放进去之前逐行念一遍：这些行是不是在回答同一个问题。

- ✅ Text2SQL vs Text2Rule —— 同层的两条路线
- ❌ 把 Agentic 混进去 —— 它是正交扩展，另起一节
- ❌ 把「别人怎么调我们」和「我们怎么调数据」混在一张表 —— 两个调用方向，"隔离性"一列根本不是同一个意思

### 列名即比较维度

用户常直接指定列名（「场景、解释、检索的部分、查询的部分」）。**他给了就照用**，不要自作主张换。他没给时，列名要是**可判定的维度**，不是「优点 / 缺点」这种主观槽。

### 计划章节写成可执行步骤

「落地要点」这种标题是注意事项，不是步骤。规划类章节改成**执行步骤 / 验收步骤**：

- 带序号，有依赖顺序
- 每步标**负责方**（算法 / 后端 / 前端）
- 单列**前置产物**：开工前必须就位的东西
- 通过线没定就写「**待定**」，不要编数字

### 论据下沉

方案章节只留**结论和动作**。benchmark 数据、论文引用、外部案例属于「难点」和「相关工作」。在执行步骤里塞论据会被指「无关的信息太多了」。

## 4 · 易读性与格式

| 要求 | 做法 |
| --- | --- |
| **无序列表优先于段落** | 三句以上的说明就拆成 bullet |
| **实例用代码块装** | `<pre><code>`，与正文明显区分；**代码块不能嵌在列表项里**，会降级，拍平成顶层块 |
| **名词解释前置** | 出现术语就补；长文档单开一节放最前面 |
| **解释要带能说明差别的例子** | 「本体：规定『1 型糖尿病 是 糖尿病的一种』，机器就能自动把 1 型患者算进糖尿病患者」——一句话说清它比同义词表多了什么 |
| **编号与层级一致** | `6.1 · xxx`、`6.2.1 · xxx`；新增小节要**顺移后面的序号并修正交叉引用** |
| **加粗标签用名词短语** | `单仓多服务`，不是 `按业务建仓，结束分离割裂` |
| **列表项不加尾标点** | 列表本身就是分隔单位 |
| **删元评论与分量词** | 不写「这是地基」「不可违背的铁律」 |
| **中立客观** | 不用「悬案」「止血」「打架」这类戏剧化措辞 |

飞书 DocxXML 的具体坑（行内 code 不支持、block 范围替换失败、画板 SVG 限制等）见 [feishu-editing-gotchas.md](references/feishu-editing-gotchas.md)。

## 5 · 节奏

**先骨架后展开。** 先给精简版让用户审，他会指定某处再深挖；不要一次写满。

- 结构错了整章返工，内容错了重写不费事 —— 所以**先对结构，再写内容**
- 用户说「精简」时，删的是论证过程和元评论，不是信息量
- 用户说「读不懂」时，换一个**能让人看见差别**的切面重写，不是把字数加多

## 6 · 收尾自检

- [ ] 整篇能被一句话串起来，每节开头一句能独立成立
- [ ] 每张表只有一个可比维度，行与行同级
- [ ] 难点与方案逐条对应，缺口明写
- [ ] 规划章节是带序号、标负责方的步骤，不是注意事项
- [ ] 论据在「难点 / 相关工作」，不在「方案」
- [ ] 术语都有解释，解释带例子
- [ ] 标题编号连续，层级不跳级，改过编号后交叉引用已同步
- [ ] 用户的段落、表格结构、配色完好
- [ ] 每条写进去的数字都查证过或标了来源与局限
